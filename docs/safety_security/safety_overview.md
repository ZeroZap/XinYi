一般安全范围
安全委员会的总体目标是针对有限的源代码范围（具体认证范围待定）获得IEC 61508标准认证和安全完整性等级（SIL）3/系统能力（SC）3认证。由于代码库已存在，我们采用IEC 61508标准定义的3S/1S路径方法。

3号公路
对不合规开发进行评估。这基本上就是利用现有资源的第一步。

1号公路
合规开发。符合本标准中关于避免和控制软件系统性缺陷的要求。

IEC 61508 标准概述
IEC 61508 标准是电气、电子和可编程电子安全相关系统功能安全的国际公认标准。以下概述了该标准的一些关键安全方面：

危险和风险分析：IEC 61508 标准要求对系统相关的潜在危险和风险进行彻底分析，以确定将这些风险降低到可接受水平所需的适当安全措施。

安全完整性等级 (SIL)：该标准引入了安全完整性等级 (SIL) 的概念，用于对每项安全功能所需的风险降低级别进行分类。SIL 等级越高，所需的风险降低级别就越高。

系统设计：IEC 61508 标准要求采用系统设计方法，包括识别安全要求、制定安全计划以及使用适当的安全技术和措施，以确保系统满足所需的 SIL 等级。

验证与确认：该标准要求对安全相关系统进行严格的测试和评估，以确保其满足规定的安全完整性等级 (SIL) 和其他安全要求。这包括系统设计验证、系统功能确认以及系统的持续监控和维护。

文件记录和可追溯性：IEC 61508 标准要求进行全面的文件记录流程，以确保安全相关系统的各个方面都得到充分记录，并且从安全要求到最终系统设计和实施都具有完全可追溯性。

总体而言，IEC 61508 标准为安全相关系统的设计、开发和实施提供了一个框架，旨在降低事故风险并提高整体安全性。遵循该标准，组织可以确保其安全相关系统的设计和实施达到最高的安全完整性水平。

为什么选择IEC 61508？
之所以选择IEC 61508标准，是因为它是一项基础性的功能安全标准，适用于各个行业领域。它提供了一个强大的框架，可作为不同行业特定标准的基础。这使得IEC 61508与Zephyr尤为相关，因为该操作系统的通用性使其能够有效地应用于广泛的行业领域。

质量
质量是整个行业对软件的强制性要求。项目代码库必须达到各种软件质量目标，才能从安全角度被视为可审计代码库，并可用于认证。但软件质量并非功能安全标准所要求的额外条件。功能安全将质量视为一项既定的前提条件，因此，无论功能安全目标如何，任何项目都应追求“质量管理”状态。以下列表描述了为实现可审计代码库需要达到的质量目标：

基本软件质量标准 - 安全视图
本章中，安全委员会阐述了为何需要上述质量目标作为前提条件，以及从安全角度出发，为实现可审计的代码库需要采取哪些措施。总的来说，所有这些与安全相关的质量措施都是为了最大限度地降低代码开发过程中的错误率。

编码指南
编码规范是工业软件产品达成共识、建立统一规则集和开发风格的基础。编码规范对于安全性至关重要，除了作为统一规则集之外，它还有其他用途。此外，它还必须证明开发人员遵循统一的开发风格，以防止软件开发过程中出现系统性错误，从而最大限度地降低整个软件系统的整体错误率。

此外，IEC 61508 标准还规定了使用编码标准/指南的前提条件和建议，以减少出错的可能性。

项目技术指导委员会 (TSC) 和项目安全委员会一致同意采用分阶段、循序渐进的方式来遵守一套编码规则（又称编码指南），以提高代码库的质量和一致性。以下是商定的阶段：

第一阶段（已完成）
编码规范规则可供遵循和参考，但目前不强制执行。这些规则在持续集成（CI）中尚未强制执行，审核人员/审批人员无法因违反规范而阻止拉取请求。

第二阶段
审核员/批准员可以阻止代码库中任何违反编码规范的拉取请求。

首先在代码库的有限范围内开始强制执行。最初，这指的是安全认证的范围。对于易于在整个代码库中应用的规则，我们不应将合规范围限制在初始范围内。这一步骤需要工具、持续集成 (CI) 设置和强制执行策略。

第三阶段
重新审视编码规范规则，并根据前几个阶段的经验，对选定的规则进行完善/迭代。

第四阶段
将执法范围扩大到更广泛的代码库。对于代码库的某些部分，如有正当理由，可酌情给予例外。例外申请需经技术服务委员会 (TSC) 批准。

需求和需求跟踪
需求和需求管理不仅对软件开发至关重要，而且对软件安全也至关重要。一方面，需求和需求管理在技术层面上详细规定和描述了软件应该实现的功能；另一方面，它也是验证所描述的功能是否按预期实现的重要且必要的工具。为此，需要将需求追溯到代码层面。通过需求管理和追溯，可以验证功能是否经过测试并正确实现，从而最大限度地降低系统性错误率。

此外，IEC 61508 标准强烈建议（对于认证而言，这几乎是必备的）要求和要求追溯。

测试覆盖率
高测试覆盖率反过来又证明了代码的安全性，表明代码完全符合其开发目标，并且不会执行任何未预料到的指令。如果对整个代码进行测试并达到高（理想情况下为 100%）的测试覆盖率，则还能快速检测到错误变更，从而进一步降低错误率。然而，必须注意的是，测试覆盖率对安全性的要求有所不同，需要考虑各种指标，这些指标由 IEC 61508 标准针对 SIL 3 / SC3 目标规定。除其他事项外，还必须满足以下条件：

结构测试覆盖率（入口点）100%

结构测试覆盖率（语句）100%

结构测试覆盖率（分支）100%

如果无法达到 100% 的覆盖率（例如防御性代码的语句覆盖率），则需要在文档中描述并证明该部分的存在。

软件架构设计原则
为了创建和维护结构化的软件产品，还必须考虑各个软件架构设计，并根据安全标准进行实施，因为某些设计和实现方式在安全性方面并不合理，这样才能确保整个软件和代码库可作为可审计代码使用。然而，Zephyr 项目中大部分此类软件架构设计已经实现，需要由安全委员会/安全工作组和安全架构师进行验证。

分层架构模型
IEC 61508 标准强烈建议采用模块化软件架构。Zephyr 项目从一开始就采用了这种分层架构。该架构的核心思想是将功能相似的模块或组件组织成不同的层。这样，每一层都可以在系统中扮演特定的角色。这种模型在安全性方面具有优势，因为不同组件和层之间的接口可以清晰地展现出来，从而可以确定哪些功能与安全相关并加以限制。此外，还可以基于这种架构构建各种分析和文档，这对于认证以及负责认证的机构至关重要。

封装组件
在现阶段，封装组件是架构设计中保障安全的关键组成部分。其中最重要的方面是将安全相关组件与非安全相关组件（包括它们各自的接口）完全分离。这确保了各个组件之间不会 相互影响。

封装单一功能（如果安全性不合理且不可管理）
整个系统和软件环境的另一个要求是，组件内的各个功能可以禁用。这是因为，如果某个功能出于安全考虑绝对不可接受（例如完全动态的内存管理），那么这些功能就应该能够被关闭。Zephyr 项目已经通过使用 Kconfig 及其灵活的配置功能提供了这种可能性。

该图描述了安全委员会为确保 Zephyr 项目开发过程中的安全而制定的大致流程。为了便于理解，需要重点强调几点，并解释安全架构师和安全委员会在整个流程中的作用。该图仅描述了与安全相关的变更可能采取的路径。

在主分支上，应明确项目的安全范围，这通常代表整个代码库的一小部分。在主分支的正常开发过程中，应确保该子集可审计，这意味着要特别关注该范围内的质量目标（Quality）和安全流程。安全架构师与技术指导委员会（TSC）密切合作，监控开发过程，以确保架构满足安全要求。

此时，安全架构师扮演着日益重要的角色。对于属于安全范围的拉取请求/问题，理想情况下，安全架构师应参与安全范围内细微变更的讨论和决策，以便能够对不符合规范的安全相关变更做出反应。如果拉取请求或问题引入了重大且影响深远的变更或改进，需要进行更深入的讨论或决策，则安全架构师应酌情将其提交给安全委员会或技术指导委员会 (TSC)，以便他们能够确定最佳行动方案。

本节介绍认证方面的内容。此时，代码库必须处于“可审计”状态，理想情况下，不应再对代码库进行任何更改。主分支与此区域之间仍然存在一条路径。这是因为，如果在创建长期支持版本 (LTS) 和可审计分支之后，在安全范围内的主分支上发现或实施了严重缺陷或重要变更，则需要这条路径。在这种情况下，安全委员会必须与安全架构师一起决定是否应将此缺陷修复或变更集成到 LTS 中，以便也能将其集成到可审计分支中。这种集成可以采取三种形式：第一种是仅进行代码更改；第二种是仅更新安全文档；第三种是两者兼而有之。

这部分描述了认证本身所需的必要安全流程。在此阶段，将创建并执行最终的分析、测试和文件，这些分析、测试和文件必须在认证过程中创建和执行，并由认证机构和被认证标准规定。如果认证机构批准此阶段的所有内容，并且安全流程已完成，则可以创建并发布安全发布文件。

从可审计分支到主分支的这种转换仅应在特殊情况下发生，尤其是在认证过程中发现某些需要快速在“可审计”分支上进行调整才能获得认证的情况时。为了防止此类问题在下次认证中再次出现，必须建立一条途径将这些更改合并回主分支，以免丢失，并在必要时为下次认证做好准备。

重要的

安全不应阻碍项目进展，也不应以任何方式限制其发展空间。
